### Kubernetes Architecture

Kubernetes mainly has **2 sides: Control Plane and Worker Nodes**.

**1. Control Plane — Brain of Kubernetes**

**API Server (`kube-apiserver`)**

* Main entry point to the Kubernetes cluster.
* `kubectl`, UI, Terraform and other tools communicate with the API Server.
* Validates and processes API requests.
* All major Kubernetes components communicate through the API Server.
* Example: `kubectl create deployment nginx --image=nginx` → request first reaches API Server.

**etcd**

* Kubernetes cluster database.
* Distributed key-value store.
* Stores cluster state and configuration.
* Stores information about Pods, Nodes, Deployments, Services, Secrets, ConfigMaps, etc.
* Think of **etcd as Kubernetes' source of truth**.

**Scheduler (`kube-scheduler`)**

* Watches for newly created Pods that don't yet have a node.
* Selects the best Worker Node.
* Considers CPU, memory, affinity/anti-affinity, taints/tolerations and other scheduling constraints.
* Important: Scheduler **selects the node; it doesn't itself start the container**.

**Controller Manager (`kube-controller-manager`)**

* Continuously checks **Desired State vs Actual State**.
* Runs controllers such as Deployment, ReplicaSet and Node controllers.
* Example: Desired replicas = 3, actual Pods = 2 → controllers work to bring the cluster back toward 3.

**Cloud Controller Manager**

* Connects Kubernetes with cloud-provider infrastructure.
* Relevant when Kubernetes runs on platforms such as AWS, Azure or GCP.
* Helps integrate cloud-specific resources such as Load Balancers, Nodes and Routes.

### 2. Worker Node — Where applications actually run

**Kubelet**

* Agent running on every Worker Node.
* Communicates with the API Server.
* Makes sure the Pods assigned to its node are running.
* Works with the container runtime to start containers.
* Reports Pod/Node status back to the control plane.

**Container Runtime**

* Actually runs the containers.
* Pulls container images and creates/starts/stops containers.
* Common Kubernetes runtimes include **containerd** and **CRI-O**.

**kube-proxy**

* Handles Kubernetes Service networking on nodes.
* Maintains networking rules so traffic can reach Service backends.
* Traditionally works using mechanisms such as iptables or IPVS.

**Pod**

* Smallest deployable unit in Kubernetes.
* Contains one or more containers.
* Containers inside the same Pod share networking and can share storage volumes.

### Simple flow to remember

```text
kubectl
   |
   v
API Server <------> etcd
   |
   +------> Scheduler
   |
   +------> Controller Manager
   |
   v
Worker Node
   |
 Kubelet
   |
Container Runtime
   |
   v
  POD
```

For example, when you run:

```bash
kubectl create deployment nginx --image=nginx --replicas=3
```

Think of the flow as:

**kubectl → API Server → etcd → Controller → Scheduler → API Server → Kubelet → Container Runtime → Pods**

A very easy interview memory trick is:

**API Server = Gateway
etcd = Database
Scheduler = Decides WHERE
Controller Manager = Maintains desired state
Kubelet = Node agent
Container Runtime = Runs containers
kube-proxy = Service networking
Pod = Runs application containers**
