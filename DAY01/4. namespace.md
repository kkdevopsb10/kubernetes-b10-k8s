### Kubernetes Namespaces

A **Namespace is a logical partition inside a Kubernetes cluster**. It helps us organize resources, separate teams/environments, apply access control, define quotas, and manage policies.

Think of it like this:

```text
One Kubernetes Cluster
        |
        +---- Namespace: dev
        |       Pods
        |       Services
        |       Deployments
        |
        +---- Namespace: test
        |       Pods
        |       Services
        |       Deployments
        |
        +---- Namespace: prod
                Pods
                Services
                Deployments
```

The important point is:

**Namespace gives logical isolation, not complete physical isolation.**

For example, `dev` and `prod` can exist in the same Kubernetes cluster, but we can apply different permissions, quotas and network rules to each.

### Why do we need Namespaces?

Suppose one Kubernetes cluster is being used by multiple teams:

```text
Kubernetes Cluster
 |
 +-- dev namespace
 |
 +-- testing namespace
 |
 +-- staging namespace
 |
 +-- production namespace
```

Without namespaces, all applications and resources would be mixed together.

Namespaces help with:

* Environment separation: Dev, Test, QA, Stage, Prod
* Team separation: Team-A, Team-B, Team-C
* Resource organization
* Resource quotas
* RBAC/access control
* Network Policies
* Avoiding resource-name conflicts
* Multi-tenant clusters
* Easier troubleshooting and administration

For example, both namespaces can have a Pod called `nginx`:

```text
dev/nginx
prod/nginx
```

That is valid because resource names need to be unique **inside a namespace**, not across all namespaces.

## 1. Create a Namespace

Using YAML:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: my-namespace
  labels:
    name: my-namespace
```

Apply it:

```bash
kubectl apply -f namespace.yaml
```

Or directly:

```bash
kubectl create namespace my-namespace
```

Short command:

```bash
kubectl create ns my-namespace
```

---

## 2. List Namespaces

```bash
kubectl get namespaces
```

Short form:

```bash
kubectl get ns
```

Usually you will see namespaces such as:

```text
NAME              STATUS
default           Active
kube-system       Active
kube-public       Active
kube-node-lease   Active
```

---

## 3. Default Kubernetes Namespaces

Kubernetes normally creates several namespaces automatically.

| Namespace         | Purpose                                                     |
| ----------------- | ----------------------------------------------------------- |
| `default`         | Resources created without explicitly specifying a namespace |
| `kube-system`     | Kubernetes/system components                                |
| `kube-public`     | Publicly readable cluster information                       |
| `kube-node-lease` | Node heartbeat/lease information                            |

Example:

```bash
kubectl get pods -n kube-system
```

You may see components such as CoreDNS there.

---

## 4. View Namespace Details

```bash
kubectl describe namespace my-namespace
```

or:

```bash
kubectl describe ns my-namespace
```

This can show information such as:

* Labels
* Annotations
* Status
* Resource quotas
* LimitRanges

---

## 5. Create Resources Inside a Namespace

Example Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: my-namespace
spec:
  containers:
    - name: nginx123
      image: nginx
```

Apply:

```bash
kubectl apply -f pod.yaml
```

Now this Pod belongs to:

```text
my-namespace
```

Check it:

```bash
kubectl get pods -n my-namespace
```

---

## 6. Namespace Using Command Line

Instead of adding:

```yaml
namespace: my-namespace
```

inside YAML, you can also run:

```bash
kubectl apply -f pod.yaml -n my-namespace
```

Similarly:

```bash
kubectl get pods -n my-namespace
```

```bash
kubectl get svc -n my-namespace
```

```bash
kubectl get deployments -n my-namespace
```

---

## 7. Switch Default Namespace

Normally:

```bash
kubectl get pods
```

checks the current/default namespace.

You can change your current context:

```bash
kubectl config set-context --current --namespace=test
```

After this:

```bash
kubectl get pods
```

automatically checks the `test` namespace.

Verify:

```bash
kubectl config view --minify | grep namespace
```

To switch back:

```bash
kubectl config set-context --current --namespace=default
```

## 8. ResourceQuota with Namespace

One of the most important Namespace use cases.

Suppose Team A should create maximum 10 Pods.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: my-resource-quota
  namespace: test
spec:
  hard:
    pods: "10"
```

Apply:

```bash
kubectl apply -f quota.yaml
```

Check:

```bash
kubectl get resourcequota -n test
```

or:

```bash
kubectl describe resourcequota my-resource-quota -n test
```

You can also restrict resources such as:

```yaml
hard:
  requests.cpu: "4"
  requests.memory: 8Gi
  limits.cpu: "8"
  limits.memory: 16Gi
  pods: "20"
```

This prevents one team from consuming the entire cluster.

## 9. Namespace + RBAC

Namespaces are frequently combined with RBAC.

For example:

```text
Developer A
    |
    | allowed
    v
DEV Namespace

Developer A
    X
    | not allowed
    v
PROD Namespace
```

You can configure:

```text
Role
RoleBinding
```

inside a namespace.

Example requirement:

> Developers can create Pods in `dev`, but cannot access `prod`.

That is a very common real-time use case.

---

## 10. Namespace + NetworkPolicy

Namespaces can also help control application communication.

Example:

```text
frontend namespace
       |
       | allowed
       v
backend namespace

test namespace
       X
       |
       v
backend namespace
```

Using Kubernetes NetworkPolicy, you can control which Pods or namespaces can communicate.

Important teaching point:

**Namespace itself does not block networking.**

You need **NetworkPolicy** for network isolation.

## 11. Namespaced vs Cluster-Scoped Resources

Very important interview topic.

### Namespaced resources

These usually belong to a Namespace:

```text
Pods
Deployments
ReplicaSets
Services
ConfigMaps
Secrets
StatefulSets
DaemonSets
Jobs
CronJobs
PVC
Role
RoleBinding
```

Example:

```bash
kubectl get pods -n dev
```

### Cluster-scoped resources

These do **not** belong to one Namespace:

```text
Nodes
Namespaces
PersistentVolumes
StorageClasses
ClusterRoles
ClusterRoleBindings
CustomResourceDefinitions
```

Example:

```bash
kubectl get nodes
```

Notice we normally don't use:

```bash
-n dev
```

for Nodes.

---

## 12. Check Which Resources Are Namespaced

Very useful command:

```bash
kubectl api-resources --namespaced=true
```

For cluster-scoped resources:

```bash
kubectl api-resources --namespaced=false
```

This is excellent for interviews.

---

## 13. Get Resources from All Namespaces

Instead of checking one Namespace:

```bash
kubectl get pods -n dev
```

check all:

```bash
kubectl get pods --all-namespaces
```

Short form:

```bash
kubectl get pods -A
```

Similarly:

```bash
kubectl get svc -A
```

```bash
kubectl get deployments -A
```

---

## 14. Delete a Namespace

```bash
kubectl delete namespace my-namespace
```

Important warning:

**Deleting a Namespace deletes the namespaced resources inside it.**

For example:

```text
delete namespace dev

      ↓

Pods        deleted
Services    deleted
Deployment  deleted
ConfigMaps  deleted
Secrets     deleted
PVCs        deleted
```

So be extremely careful with production namespaces.

## 15. Real-Time Example

Imagine your company has:

```text
Kubernetes Cluster
│
├── development
│   ├── frontend
│   ├── backend
│   └── database
│
├── testing
│   ├── frontend
│   ├── backend
│   └── database
│
└── production
    ├── frontend
    ├── backend
    └── database
```

Now you can apply:

```text
Development
CPU: 4
Memory: 8 GB

Testing
CPU: 8
Memory: 16 GB

Production
CPU: 40
Memory: 80 GB
```

You can also apply different:

```text
RBAC
ResourceQuota
LimitRange
NetworkPolicy
Secrets
Policies
```

for every environment.

## Important Namespace Commands for Students

```bash
# List namespaces
kubectl get ns

# Create
kubectl create ns dev

# Delete
kubectl delete ns dev

# Details
kubectl describe ns dev

# Get pods
kubectl get pods -n dev

# Get services
kubectl get svc -n dev

# Get deployments
kubectl get deployments -n dev

# All namespaces
kubectl get pods -A

# Switch current namespace
kubectl config set-context --current --namespace=dev

# Check current namespace
kubectl config view --minify | grep namespace

# Check namespaced resources
kubectl api-resources --namespaced=true

# Check cluster scoped resources
kubectl api-resources --namespaced=false
```

### Best sentence to explain

> **Kubernetes Namespace is a logical boundary used to organize cluster resources and apply separate RBAC, ResourceQuota, LimitRange and NetworkPolicy rules for different teams or environments.**

And one important interview correction:

> **Namespace provides logical separation, but Namespace alone does not provide complete security or network isolation.**

You usually combine it with **RBAC + NetworkPolicy + ResourceQuota + LimitRange**.
