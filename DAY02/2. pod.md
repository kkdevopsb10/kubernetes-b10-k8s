### What is a Pod?

A **Pod is the smallest deployable and schedulable unit in Kubernetes**.

Kubernetes does not normally manage containers directly. It manages **Pods**, and Pods contain one or more containers.

```text
Kubernetes Cluster
       |
       +--- Worker Node 1
       |        |
       |        +--- Pod
       |             |
       |             +--- Container
       |
       +--- Worker Node 2
                |
                +--- Pod
                     |
                     +--- Container
```

A good classroom sentence is:

**Container runs the application. Pod provides the Kubernetes wrapper around that container.**

### Important Pod Points

* A Pod always runs on a **Worker Node**.
* A Pod represents a running instance of an application workload.
* A Pod can contain **one or more containers**.
* All containers inside the same Pod share the **same network namespace**.
* Containers in the same Pod share the same Pod IP.
* They can communicate with each other using `localhost`.
* Containers can also share mounted volumes.
* Every Pod gets its own cluster IP address.
* Pods are **ephemeral**.
* A Pod can be created, deleted and recreated frequently.
* You generally should not manage production applications using standalone Pods.
* Use controllers such as Deployment, StatefulSet, DaemonSet or Job.

# Pod Lifecycle – How a Pod Gets Created

Suppose you execute:

```bash
kubectl apply -f pod.yaml
```

The flow is:

```text
User
 |
 | kubectl apply
 v
API Server
 |
 +---- Validate YAML/API Request
 |
 v
etcd
 |
 | Pod desired state stored
 v
Scheduler
 |
 | Select best Worker Node
 v
API Server
 |
 v
Kubelet on Worker Node
 |
 v
Container Runtime
 |
 | Pull image
 | Create container
 | Start container
 v
Pod Running
```

### Step-by-step

**1. User submits Pod request**

```bash
kubectl apply -f pod.yaml
```

The request goes to the **API Server**.

**2. API Server validates it**

The API Server checks whether the request and YAML specification are valid.

**3. Desired state is persisted in etcd**

The cluster state is stored through the API Server in etcd.

**4. Scheduler finds an unscheduled Pod**

Initially the Pod has no assigned worker node.

Scheduler checks:

* CPU
* Memory
* Taints/Tolerations
* Affinity
* NodeSelector
* Scheduling constraints

and selects an appropriate node.

**5. Kubelet notices the assigned Pod**

Kubelet running on that Worker Node watches the API Server.

**6. Container runtime starts containers**

For example, containerd:

```text
Pull Image
   ↓
Create Container
   ↓
Start Container
```

**7. Pod enters Running state**

Kubelet keeps reporting its status to the control plane.

# Important Correction

Your original point says:

> Pod is ephemeral and won't be rescheduled to a new node once it dies.

A clearer explanation is:

**The same Pod is not moved from one Node to another.**

If a Pod disappears and it is managed by a controller such as Deployment, Kubernetes usually creates a **new replacement Pod**.

For example:

```text
Before Failure

Node-1
 |
 +-- Pod-A
     IP: 10.244.1.5


Node-1 Failure
       ↓

Deployment detects missing Pod
       ↓

Node-2
 |
 +-- Pod-B
     IP: 10.244.2.8
```

`Pod-B` is a **new Pod**, not Pod-A moved to Node-2.

This is a very important interview concept.

# Pod Is Ephemeral

Ephemeral means:

**temporary and replaceable.**

Pods are not designed like permanent virtual machines.

```text
VM mindset
Server → Keep same machine alive

Kubernetes mindset
Pod → Replace it when necessary
```

This is why applications should not depend on a specific Pod IP.

# Two Common Pod Models

## 1. One Container Per Pod

This is the most common model.

```text
+------------------+
|       POD        |
|                  |
|   +----------+   |
|   |   Nginx  |   |
|   |Container |   |
|   +----------+   |
+------------------+
```

Example:

```text
Pod
 |
 +-- Java Application Container
```

Kubernetes manages the **Pod**, while the Pod wraps the container.

# 2. Multi-Container Pod

A Pod can contain multiple tightly related containers.

```text
+--------------------------------+
|              POD               |
|                                |
| +-------------+ +------------+ |
| | Application | |   Sidecar  | |
| | Container   | | Container  | |
| +-------------+ +------------+ |
|                                |
| Shared Network                 |
| Shared Storage                 |
+--------------------------------+
```

Typical examples:

```text
Main Application
       +
Log Agent

Main Application
       +
Proxy

Main Application
       +
Monitoring Helper
```

The important rule is:

**Put containers in the same Pod when they are tightly coupled and need to share lifecycle, networking, or storage.**

# Communication Inside a Multi-Container Pod

Suppose:


They can communicate through:


because they share the same Pod network namespace.

# Pod YAML Structure


```text
    ↓

```

# Pod Status / Phase

You will commonly see:

```text
Pending
Running
Succeeded
Failed
Unknown
```

### Pending

Pod was accepted by Kubernetes but is not fully running yet.

Possible reasons:

* Scheduler hasn't assigned node
* Insufficient CPU
* Insufficient memory
* PVC pending
* Image is still being pulled

### Running

Pod is assigned to a Node and at least one container has been started.

### Succeeded

All containers completed successfully and will not restart.

Common with:

```text
Jobs
Batch workloads
```

### Failed

Containers terminated and at least one terminated unsuccessfully.

### Unknown

Kubernetes cannot determine the Pod state, often because communication with the Node is lost.

# What Does READY 1/1 Mean?

Example:

```text
NAME       READY
nginx      1/1
```

`1/1` means:

```text
Ready Containers / Total Containers
```

So:

```text
1/1
```

means:

**1 container is Ready out of 1 container.**

```text
2/2
```

means:

**2 containers are Ready out of 2.**

```text
1/2
```

means:

**Only 1 of 2 containers is Ready.**

```text
0/2
```

means:

**Neither container is Ready.**

One important refinement: READY indicates **readiness**, not simply whether a process exists.

A container may technically be running but still show:

```text
0/1
```

if its readiness probe is failing.

This is an excellent interview point.

---

# READY vs STATUS

You might see:

```text
NAME     READY   STATUS
app      0/1     Running
```

Students sometimes ask:

**How can STATUS be Running while READY is 0/1?**

Because:

```text
Container process started
        ↓
STATUS = Running

But application is not ready for traffic
        ↓
READY = 0/1
```

For example, readiness probe fails.

# Before Creating the Pod — Validation / Sanity Check

Instead of relying on verbose mode as the main validation technique, use:

```bash
kubectl apply -f pod.yaml --dry-run=client
```

Better still:

```bash
kubectl apply -f pod.yaml --dry-run=client -o yaml
```

This validates client-side processing without actually creating the object.

You can also use:

```bash
kubectl apply -f pod.yaml -v=8
```

for **verbose debugging**, but `-v=8` is mainly for troubleshooting kubectl/API communication, not the primary YAML sanity check.

That distinction is good to teach students.

# Why We Should Not Normally Create Standalone Pods

Suppose you create:

```bash
kubectl apply -f nginx-pod.yaml
```

and the Pod gets deleted.

There is no controller ensuring another copy exists.

```text
Standalone Pod

Pod
 |
 X deleted
 |
Application Down
```

Compare that with Deployment:

```text
Deployment
   |
ReplicaSet
   |
  Pods

One Pod dies
     ↓
ReplicaSet detects it
     ↓
New Pod created
```

So in production:

**Don't think “create Pod.” Think “create a controller that manages Pods.”**

# Pod Networking

Every Pod normally gets its own IP.

```text
Pod-A
10.244.1.5

        ↓ Network

Pod-B
10.244.2.7
```

But remember:

**Pod IPs are temporary.**

When a replacement Pod is created:

```text
Old Pod
10.244.1.5
   X

New Pod
10.244.2.10
```

This is one reason Kubernetes **Services** are important.

```text
Client
  |
Service
  |
  +---- Pod-A
  +---- Pod-B
  +---- Pod-C
```

Service gives applications a more stable way to reach Pods.

# Pod Interview Questions

**Q: What is a Pod?**

A Pod is the smallest deployable and schedulable unit in Kubernetes that contains one or more containers.

**Q: Can one Pod have multiple containers?**

Yes. Containers inside the same Pod share networking and can share storage.

**Q: Does Kubernetes schedule containers?**

Technically Kubernetes scheduling operates on **Pods**, not individual containers.

**Q: Can two Pods have the same IP?**

Normally active Pods in a cluster network have unique Pod IPs.

**Q: Can containers inside the same Pod talk through localhost?**

Yes.

**Q: Does a Pod move to another Node when its Node fails?**

No. A controller can create a **new replacement Pod** on another Node.

**Q: Should we deploy production applications using standalone Pods?**

Normally no. Use controllers such as Deployment or StatefulSet.

**Q: What is 1/2?**

One of two containers is Ready.
